--------------------------------------------------------------------------------
1. OFFLINE ANALYSIS / NATURAL-LANGUAGE QUERIES
--------------------------------------------------------------------------------
Goal examples:
    - "What is my average running speed in the last 10 workouts?"
    - "How frequently did I work out in the last 6 months?"
    - "How often do I stop running and switch to walking?"

Current state:
    - History is stored as JSON blobs in SharedPreferences (WorkoutHistory).
    - Good for a simple list; not suitable for aggregate queries.

Recommended architecture:
    - LOCAL DB: Room (SQLite) - the Android standard.
        Tables:
            * workouts          (id, date, totals...)
            * activity_periods  (workout_id, type, steps, distance,
                                 duration, start, end)
            * gps_points        (optional: workout_id, lat, lon, time, accuracy)
        Most questions ("average speed over last 10", "frequency over 6 months",
        "walk<->run transition count") are answered with plain SQL - no AI needed.

    - NATURAL-LANGUAGE -> QUERY (the AI part):
        * On-device LLM (Gemini Nano via ML Kit / AICore on Pixel & recent
          Samsung; or a small GGUF model via llama.cpp / MediaPipe LLM Inference)
          translates the question into a PARAMETERIZED query.
        * Safety: map the model output to a fixed set of query templates rather
          than letting it emit raw SQL.

About MCP (Model Context Protocol):
    - Conceptually a great fit: expose tools like avg_speed(last_n),
      workout_frequency(months), transition_count() - exactly like the existing
      flights MCP server.
    - BUT MCP is a desktop/server protocol (stdio/HTTP to a host such as
      Cursor/Claude). It does NOT run inside an Android app. Two realistic paths:
        a) CLOUD: phone -> your backend hosting an MCP server + LLM.
           Online only, needs servers, privacy tradeoff.
        b) ON-DEVICE: skip MCP; implement the same "tools" as Kotlin functions
           the local LLM calls (function-calling). Same UX, fully offline.
    - Best near-term use of MCP: a COMPANION DESKTOP experience (existing
      Cursor/Claude setup querying an exported DB), not embedded in the phone.

Complexity:
    - Room migration:           LOW-MEDIUM (~1-2 days)
    - On-device NL querying:    MEDIUM-HIGH (device fragmentation; model 1-4 GB;
                                not all phones support Gemini Nano)
    - Cloud LLM querying:       MEDIUM (recurring cost + privacy considerations)


--------------------------------------------------------------------------------
2. SUGGESTED FUTURE WORKOUT PLANS (INTERACTIVE)
--------------------------------------------------------------------------------
Goal:
    - Generate future plans from workout history (e.g. progressive Couch-to-5K).
    - Be interactive and cooperate with the user's expectations/goals.

Notes:
    - Output slots directly into the existing ScheduleItem model / schedule system.
    - RULE-BASED generator ("last avg run was 6 min, add 10% next week") gives
      ~80% of the value with no AI.
    - LLM-DRIVEN conversational planner ("I want to run 5K in 8 weeks") that asks
      clarifying questions builds on top of feature #1's LLM infrastructure.

Complexity:
    - Rule-based plan generator:        LOW
    - LLM conversational planner:       MEDIUM (requires #1's LLM stack)


--------------------------------------------------------------------------------
3. MOTIVATIONAL SENTENCES DURING WORKOUT
--------------------------------------------------------------------------------
Goal:
    - Show motivating messages during a workout.

Notes:
    - Easiest, highest ROI. A curated/templated pool keyed off live state
      ("2 km in - keep the pace!", "halfway through your jog interval").
    - Works offline today, no model needed.
    - LLM-generated personalized lines are possible but overkill; pre-written +
      variable interpolation avoids latency/cost.

Complexity:
    - Templated pool:           LOW
    - LLM-generated lines:      LOW-MEDIUM (not recommended as first step)

4. ADDITIONAL IDEAS WORTH CONSIDERING
--------------------------------------------------------------------------------
    - Auto workout summary & insights ("you ran 12% faster than your 4-week
      average") - pairs with the Room DB; mostly stats, not AI.        [LOW-MED]
    - Anomaly/form feedback from the accelerometer (irregular cadence,
      overstriding) - needs signal processing / ML.                    [HIGH]
    - Smart auto-pause (detect you stopped) - cheap, big UX win.        [LOW-MED]
    - Voice coaching (TTS of motivational + interval cues) via the
      Android TextToSpeech API.                                        [LOW]
    - Weekly goals + streaks + notifications - engagement driver.       [LOW]


--------------------------------------------------------------------------------
OVERALL COMPLEXITY VERDICT FOR A MOBILE APP
--------------------------------------------------------------------------------
    - Stats/DB, rule-based plans, motivation, TTS, streaks:
        All LOW-MEDIUM, ship-able without any LLM. Do these first.

    - Natural-language queries + conversational planning:
        The genuinely "AI" parts. On-device LLMs on Android are viable but
        bleeding-edge (Gemini Nano / MediaPipe LLM Inference) - limited device
        support, large downloads. Cloud LLM is easier to build but adds servers,
        cost, and a privacy story (location/health data).

    - MCP specifically:
        Best as a companion DESKTOP experience (Cursor/Claude querying an
        exported DB), not embedded in the phone app.

RECOMMENDED FIRST STEP:
    Migrate history from JSON (SharedPreferences) to a Room database.
    It unlocks features #1, #2, and the insights with the least risk.
    Scaffolding: entities, DAO, and a migration from the existing JSON.
